## Composite-score-vs-interview-date defect: RESOLVED as a CONFIRMED BUG

The planning step's suspicion — that the "Recruit + OM + HR + TL" column actually displays the row's Interview Date rather than a distinct composite score — was re-checked across **3 different candidate rows** (the entire seeded Following-Up dataset, found by widening the date range to 1 Feb 2026 – 28 Aug 2026; no further rows exist even back to 1 Feb 2025) and is **CONFIRMED as a real defect**, not a one-row misread.

Evidence (all three rows, same widened date range, one screenshot):

| Row | Candidate | "Recruit + OM + HR + TL" column value | Quiz | Coding | Grade |
|---|---|---|---|---|---|
| 1 | Miss. Vannyda PICH | `24/Aug/26 10:28 AM` | `-` | `-` | `N/A` |
| 2 | Ms. Windy QA | `-` | `-` | `-` | `N/A` |
| 3 | Ms. Raksa CHANN | `30/Jun/26 10:32 AM` | `48/50` | `80/100` | `B` |

- Rows 1 and 3 both show a value in exactly the `DD/Mon/YY HH:MM AM/PM` timestamp format under the "Recruit + OM + HR + TL" header — never a numeric/percentage score of any kind.
- Row 3 (Raksa CHANN) is the most damning sample: she has **real, populated** Quiz (`48/50`), Coding (`80/100`) and Grade (`B`) values in their own correctly-positioned columns, proving the row's scoring data is genuinely present and rendered correctly elsewhere — yet the column literally labeled "Recruit + OM + HR + TL" still shows a date/time, not a fourth score.
- Opening Raksa CHANN's own candidate-profile modal (via her name button) surfaces a **separate, genuine composite-style summary** under an "Interview" section: `OVERALL: 83.5%`, `Coding: 80%`, `Quiz: 96%`, `Average: 88%`, plus English/Flexibility/Q&A/Logical ratings. `Coding: 80%` and `Quiz: 96%` reconcile exactly with the table's own `80/100` and `48/50` (48/50 = 96%), confirming the profile modal's figures are the real, correctly-computed scores for this candidate — and that no such figure ever surfaces under the "Recruit + OM + HR + TL" label anywhere in the report table. The nearest date on the profile ("Interview (1) ... 30/Jun/2026 05:32 PM") is the same calendar day as the table's `30/Jun/26 10:32 AM`, differing only in displayed time (likely a timezone/format artifact between the two views) — additional corroboration that the table's column is rendering an interview timestamp, not a score.
- Row 2 (Windy QA) shows `-` in the same column with no Quiz/Coding/Grade data either, consistent with "no interview date recorded yet" rather than adding any counter-evidence.

**Verdict: CONFIRMED BUG.** The "Recruit + OM + HR + TL" column header is mislabeled/mis-bound — it renders the row's own Interview Date value, and no distinct composite score for Recruit/OM/HR/TL is ever shown in the report table itself (the closest equivalent, an "Overall"/"Average" percentage, only exists in the candidate profile modal, under different labels).

Evidence screenshot: `defect-RPT01-composite-score-column-shows-interview-date.png` (repo root) — full-width capture of the Following Up Report table with all 3 rows visible, showing the yellow-highlighted "Recruit + OM + HR + TL" header directly above two timestamp values and one `-`.

## Bugs / inconsistencies found

### Bug #1 (CONFIRMED, high severity) — "Recruit + OM + HR + TL" column shows the Interview Date, never a composite score
See the dedicated section above. Confirmed across all 3 seeded Following-Up rows plus corroborating evidence from the candidate profile modal. Evidence: `defect-RPT01-composite-score-column-shows-interview-date.png`.

### Bug #2 (OBSERVATION, not necessarily a defect) — Filter control disappears entirely on Summary tabs; search state is not shared across tabs
- **Where:** Advance Report page, Filter button + report's own search box.
- **Observed:** The "Filter" button (ALL/INTERN/STAFF) is rendered **only** on the Following Up Report tab — it is simply absent from the DOM on Summary Full Staff / Summary Intern (confirmed via `isVisible()` returning `false` there, and via a screenshot). The report's own search box, by contrast, **does** exist on every tab, but each tab keeps its own independent value — text typed on one tab is not carried to another, and is not cleared either (it's still there if you switch back).
- **Assessment:** Likely intentional (Filter's ALL/INTERN/STAFF concept may not be meaningful for the two Summary tabs), but worth confirming with product/design, since the test plan's App Overview note ("[Filter] applying across whichever tab is active") turns out to only be true for the Following Up tab in practice. Flagging as a documentation correction rather than a functional defect.
- **Automation impact:** A `switchTab()`-style helper must never assume the Filter control is present after switching away from Following Up Report.

### Bug #3 (reconfirmed + sharpened) — Eye-icon dialog's Quiz/Coding placeholder convention doesn't match the table's own cells for ungraded candidates
- **Where:** Eye-icon "Remark" dialog vs. the row's own Quiz/Coding table cells.
- **Observed this session, 2 samples:**
  - Vannyda PICH (ungraded): table shows Quiz `-` / Coding `-`; the eye dialog for the same row shows Quiz `N/A` / Coding `N/A` for the same (absent) values.
  - Raksa CHANN (graded): table shows Quiz `48/50` / Coding `80/100`; the eye dialog shows the **exact same** `48/50` / `80/100` — no mismatch at all.
- **Refined conclusion:** The dialog and table are **not** actually out of sync on real data — they agree perfectly once a candidate has real scores. The only inconsistency is in the **placeholder convention for an absent value**: the table uses `-`, the dialog uses `N/A`, for the identical underlying "no score yet" state. This is a smaller, more precise finding than the plan's original "values didn't match" framing suggested from its single sample.

### Bug #4 (new this session, sharpens open item #3) — The Following Up Report tab's own Remark column never renders text that the Summary Full Staff tab's Remark column shows correctly for the same candidate
- **Where:** Following Up Report tab vs. Summary Full Staff tab, both showing the same candidate (Vannyda PICH) in the same widened date range.
- **Observed:** On the Following Up Report tab, "Remark" is only a banner label sitting above the unnamed eye-icon column — there is no distinct rendered Remark **text** column at all on that tab (confirmed via colspan inspection: the banner's "Remark" `colspan=1` cell sits directly above the blank header for the eye-icon column, not above any text cell). On the Summary Full Staff tab, "Remark" **is** a genuine 8th data column, and for the exact same candidate (Vannyda PICH, row 15 in the widened range) it correctly displays `Passed.` — the same text the eye-icon dialog's Description field shows.
- **Assessment:** This is a more precise, confirmed version of the plan's open item #3. It is not that "Remark is blank until the eye icon is opened" in general — Summary Full Staff proves the underlying text is available and can render inline. It is specifically the **Following Up Report tab** that never surfaces it as text (only via the separate eye-icon dialog).
- **Evidence:** `defect-RPT08-remark-column-blank-only-on-following-up-tab.png` (repo root) — Summary Full Staff tab, row 15, showing `Passed.` in the Remark column for the same candidate whose Following Up Report row has no visible Remark text anywhere in the table itself.

### Bug #5 (new this session, corrects RPT02-2 and explains the Full Staff pagination dataset) — the Summary Full Staff / Summary Intern date-range control does not actually re-query their data; each tab's date range is independent, and Full Staff's `Total: 16` appears to be date-range-independent entirely
- **Where:** date-range pill/panel, compared across tabs.
- **Repro:** On Following Up Report, open the date-range panel, navigate the calendar back to Feb 2026 and forward to Aug 2026 (a ~7-month custom range), click Generate (banner correctly updates to `FOLLOWING-UP QUALIFIED CANDIDATES (1 Feb 2026 - 28 Aug 2026)` with 3 rows, confirmed repeatedly this session). Then switch to Summary Full Staff.
- **Observed:** Summary Full Staff's own banner reverted to (or simply never left) `FULL STAFF (24 Aug 2026 - 28 Aug 2026)` — the default current week — and its `Total: 16` was **identical** whether checked at the untouched default range or after the Following-Up-tab widening. This means either (a) each tab's date-range control keeps fully independent state (Following Up's widened range never applied to Full Staff at all, consistent with the search-box independence in Bug #2), and/or (b) the Summary tabs' underlying query does not filter by the date range control at all regardless of tab. Either way, the plan's RPT02-2 scenario ("switching tabs preserves the active date range") only holds trivially true when the range is never actually changed — its own worked example coincidentally never changes the range either.
- **Assessment:** Not confirmed which of (a)/(b) is the root cause without backend/API access, but the user-facing effect is real and worth a design/dev confirmation: a recruiter who deliberately widens the date window on one tab to find older candidates, then switches tabs expecting the same window, will silently see the Summary tabs snap back to the current week instead.
- **Practical upside for automation:** this also means Summary Full Staff's 16-row / 2-page dataset (used to resolve RPT09-2, see above) requires **no date-range setup at all** — it's present at the tab's own default view.

## Insights for automation (selectors, timing, workarounds)

1. **Login rate-limiting:** authenticate once per test file/worker and reuse the session; hammering `/welcome` with `>8` logins in quick succession can trigger a transient false "wrong username/wrong password" state that clears on its own after roughly a minute of no further attempts. Do not add retry-with-different-credentials logic — just back off and retry the same credentials.
2. **Date-range calendar navigation:** the prev/next chevrons are `<mat-icon class="... arrow ...">keyboard_arrow_left</mat-icon>` / `keyboard_arrow_right` (Material icon **text content**, not `chevron_left`/`chevron_right`) — use `page.locator('mat-icon.arrow', { hasText: 'keyboard_arrow_left' })` and `.dispatchEvent('click')` (a plain `.click()` intermittently fails with "element intercepts pointer events" from the calendar's own hover/animation layer; `.click({ force: true })` also works but `dispatchEvent('click')` was the most reliable in this session). The month/year label is `label.header-label.w-32` (there is a second, unrelated `label.header-label` reading "Calender" in the same panel — scope with `.w-32` or you'll hit a strict-mode violation). Day cells are `getByRole('gridcell', { name: /^\w+ 1,/ })`-style (full text like "August 1, 2026").
3. **Pagination page numbers are `<span class="page-note-item">`, not `<button>` or `role=button`.** The active page carries an additional `active` class (`span.page-note-item.active`). `getByRole('button', { name: '2' })` will simply never find them.
4. **Filter radio group:** `page.getByText('Filter', { exact: true }).first().click()` opens the panel; the three options are plain text nodes next to Angular Material radios (`page.getByText('STAFF', { exact: true }).click()` works directly and is simpler/more reliable than trying to scope through `mat-radio-button`/`[class*="radio"]`, which was ambiguous enough to hang a click in this session). To read the actual checked state, query `input[type="radio"]` directly (`.checked` + `.closest('mat-radio-button')?.textContent`).
5. **Excel export click does not reliably fire a Playwright `download` event within a couple of seconds** in this environment — don't assert on the `download` event as proof of success; per the plan's own scope, only assert "no new console/page error + button stays enabled," and if a real file-content check is ever added, allow a generous timeout and confirm first whether the app opens a new tab/blob URL instead of a native download.
6. **A pre-existing, unrelated console error fires on every single page load**: `Error initializing Firebase Messaging: ... Installations: Missing App configuration value: "projectId"`. Filter this out of any console/page-error assertions everywhere in this module (and likely others) — it is not caused by anything this plan's scenarios do.
7. **The report's own search box, the Filter control, and (per Bug #5) the date range itself are all tab-scoped/tab-limited state to watch for:** Filter is rendered only on Following Up Report (absent from the DOM on the two Summary tabs); the search box exists on all three tabs but holds independent per-tab state; the date-range control also appears not to carry a manual widen from one tab to another (Summary Full Staff kept showing its own default-week banner/total even after Following Up's range was deliberately widened). A future `switchAdvanceReportTab()` helper should not assume **any** filter/search/date state is shared across tabs — treat each tab as needing its own setup.
8. **To get more than 0-1 rows for any Following-Up-tab test, widen the date range to roughly `1 Feb 2026 – 28 Aug 2026`** (6 chevron-clicks back from Aug 2026, pick day 1, 6 clicks forward, pick day 28, Generate) — this is the entire seeded Following-Up dataset (3 rows: Vannyda PICH, Windy QA, Raksa CHANN); going back further (tested to Feb 2019) adds no more rows. **For a genuinely multi-page dataset, Summary Full Staff already has 16 rows / 2 pages at its own default view — no date-range setup needed there at all** (mixing real candidates with leftover synthetic `QA Automation Test CANDIDATE ...` rows from other suites).
9. **`dumpTable`-style row extraction** (`table.querySelectorAll('tr')` → map `tr.children` → `textContent`) is a fast, reliable way to snapshot an entire report table (header rows plus data rows) in one call for either tab; the first array element is always the orange banner row, the second is always the real column-header row, and everything after that is data (or a single one-cell `["No matching records found"]` row).
